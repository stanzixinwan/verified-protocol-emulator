# Personal Proposal: Verification-First Protocol Emulator

Jane Street Protocol Emulator ASIC Competition · Oct 23, 2026 · @Stan

## Problem and question

I will deliver a programmable protocol emulator for the Tiny Tapeout IHP CMOS5L 6×4-tile slot. Its hardware is generated by Claude Code and accepted only by an independent verification harness that I build.

**Core question:** how far does an AI agent get on this task in a pure software-simulation flow, and how much does independent verification change the result?

**Problem statement:** with the hardware frozen, the chip must implement UART, SPI, I2C and protocols it has never seen, through firmware alone, within the area and timing limits of the slot.

**Functional highlight:** a capture mode that records pin edges with timestamps, so the same chip can sniff and decode a protocol as well as drive it. This targets the debugging and reverse-engineering use the competition describes.

## Division of work

I write the specification and the judge; the AI writes the chip. This split plays to my strengths in Python, systems and verification, and keeps hand-written RTL at zero.

| Part | Owner | Notes |
| --- | --- | --- |
| Requirements and formal properties | Me | Traceable from user scenario to evidence |
| Verification harness and protocol checkers | Me | Python / cocotb, pin-level |
| Experiment harness and logging | Me | Agent loop, metrics, trajectories |
| Architecture and ISA | AI | Within the constraints below |
| RTL | AI | Verilog |
| Assembler and firmware | AI | One firmware per protocol |

The AI works within constraints I fix up front:

- Deterministic cycle count per instruction
- Firmware loaded after fabrication through a host interface (for example SPI from the dev board's RP2040), never hard-coded in the RTL
- Tiny Tapeout pins: dedicated inputs, dedicated outputs and bidirectional pins; I2C and 1-Wire use the bidirectional pins as open-drain lines
- Instruction memory in SRAM where possible, which is more area-efficient than flip-flops
- Open source under Apache-2.0

The checkers judge only pin waveforms, so they do not depend on whichever architecture the AI picks. The same harness can score teammates' designs.

## Comparison with PIO and PRU

The competition points to the RP2040 PIO and TI PRU. This design differs in how flexibility is defined, shown and built.

|  | RP2040 PIO | TI PRU | This design |
| --- | --- | --- | --- |
| Core | 4 small state machines per block, 9 instructions | 32-bit RISC core | Chosen by the AI within the constraints above |
| Timing | Deterministic | Deterministic | Deterministic by requirement |
| Capture | Pin sampling into FIFOs, read by the CPU | Software polling | Built-in edge capture with timestamps |
| Evidence of flexibility | Not measured | Not measured | Held-out protocols on frozen hardware |
| How it is built | Hand-designed | Hand-designed | AI-generated, independently verified |

## Trade-offs and how they relate

The seven dimensions from the meeting do not trade off pairwise. A few design knobs move several of them at once, and all knobs draw on one fixed area budget.

```latex
\text{Area} \approx \text{program memory} + \text{decode} + N_{\text{SM}} \cdot \text{SM logic} + \text{hardware assists} + \text{resilience logic} \le 6 \times 4 \text{ tiles}
```

```latex
\text{max protocol rate} \approx \frac{f_{\text{clk}}}{\text{cycles per bit}}, \qquad \text{timing resolution} = \frac{1}{f_{\text{clk}}}
```

| Knob | Turned up | Improves | Costs |
| --- | --- | --- | --- |
| Programming model (fixed config → ISA) | More general | Programmability, protocol coverage | Area; more cycles per bit, so lower max rate |
| Program memory size | Larger | Coverage of complex protocols | Area, usually the largest block |
| Number of state machines | More | Full duplex, multi-pin protocols, throughput | Area, power |
| Hardware assists (shifter, counter, CRC) | More | Max rate, latency | Area; protocol-specific assists erode flexibility |
| Timing determinism (fixed cycles per instruction) | Stricter | Latency predictability, zero jitter | Some throughput and ISA freedom |
| Resilience logic (filtering, timeouts, recovery) | More | Resilience | Area, added latency |

Three relations matter most:

- **Flexibility versus speed** is the central conflict: generality costs area and cycles per bit.
- **Assists are a trap at the extreme:** protocol-specific blocks are fast but become the fixed UART/SPI/I2C design the competition rules out. Generic assists (shift registers, counters) are the safe side.
- **Verifiability is an eighth dimension:** a more flexible architecture has a larger state space, so it is harder to verify and harder for the AI to get right.

Power follows from clock and area, and Tiny Tapeout does not report it precisely, so I report it only as an estimate.

## Objectives

I optimize for flexibility and latency predictability. Both can be measured fully in software simulation, and they pull against each other, so their frontier is worth mapping.

| Class | Dimension | Metric |
| --- | --- | --- |
| Hard constraint | Area | Fits 6×4 tiles after place and route |
| Hard constraint | Timing | Closes at 50 MHz (fallback 25 MHz); Tiny Tapeout precheck passes |
| Hard constraint | Correctness | UART, SPI, I2C pass the independent checkers |
| Primary | Flexibility | Held-out protocols implemented by firmware alone (k of 3); firmware lines per new protocol |
| Primary | Latency predictability | Min, median, p99 and worst-case latency; jitter |
| Secondary | Performance | Max rate per protocol |
| Secondary | Resilience | Fault injection, deferred to after the team merge |
| Secondary | Verifiability | Mutation-kill rate of the harness |
| Secondary | Power | Estimate only |

I2C limits are defined at protocol level only: bus rate, clock stretching, multiple targets, ACK/NACK. Electrical limits (capacitance, loading) need FPGA or real hardware and are out of scope, as are low-speed USB and 10 Mbit Ethernet.

## Verification

Every requirement traces to evidence: user scenario → requirement → formal property → test or proof → result. The harness takes a design directory and returns one JSON report per run.

1. **Protocol checkers:** independent UART, SPI and I2C models decode the pin waveforms and compare bytes, timing and handshakes. The same models check capture mode against known waveforms.
2. **Randomized tests:** random baud rates, CPOL/CPHA, word lengths, addresses, payloads; fixed seeds for reproducibility.
3. **Formal properties:** 2–3 pin-level safety properties in SVA, checked with SymbiYosys: no X after reset, no conflicting drive on bidirectional pins.
4. **Physical checks:** synthesis and place and route on every iteration; area, timing and precheck results enter the report.
5. **Held-out protocols:** PS/2, 1-Wire and one invented single-wire protocol, kept from the AI; hardware frozen, firmware only.
6. **Checking the checker:** about 20 hand-injected bugs in a passing design; the harness must catch them.

Tests are read-only to the AI, and part of the test set stays hidden.

## Experiments

Three runs answer the core question and map the trade-offs. All use the same model, token budget and iteration cap.

| Run | Setup | Answers |
| --- | --- | --- |
| E0 Baseline | Claude Code gets the competition brief and template only; it writes and tests its own design | How far plain AI gets in software simulation |
| E1 Verified loop | Same start; my harness reports after every iteration and failures feed back | What independent verification adds over E0 |
| E2 Pareto sweep | E1 at 2–3 design points, e.g. small vs large program memory, assists on or off | Where the flexibility, latency and area frontier lies |

E0 is scored afterwards by the same harness, so its self-reported completion can be compared with checked completion. Every iteration is logged: prompt, RTL diff, tool output, test results, tokens, failure type.

## Steps

The work fits five weeks. Steps 1–4 and 6 are the core; steps 5, 7 and 8 are cut first if time runs short.

1. Set up the repository from the CMOS5L template with CI green; write the specification and the AI constraints.
2. Write the UART checker; run E0 and score it.
3. Write the SPI and I2C checkers and randomized tests; connect the harness as the feedback loop (E1).
4. Add synthesis, place and route and precheck to every iteration; add the pin-level safety properties.
5. Add capture mode to the requirements, with its checker.
6. Freeze the hardware; run the held-out protocols, firmware only.
7. Build the injected-bug suite and measure the catch rate.
8. Run E2 at 2–3 design points; write up the results.

## Risks

| Risk | Mitigation |
| --- | --- |
| The AI does not converge | Cap iterations and tokens; a non-converging run is itself a result |
| Area overflow found late | Synthesis on every iteration from step 4 |
| The AI games the tests | Read-only tests, hidden tests, held-out protocols |
| My limited hardware experience | Pin-level checks need no RTL reading; teammates review physical results |
